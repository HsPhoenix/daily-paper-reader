## 摘要
代理商务平台让AI代理能够自主发现服务、移动支付并以用户名义使用用户凭证，这些平台已经在处理真实资金。迄今为止，其安全性几乎完全在AI模型层面进行研究，通过提示注入和错位（misalignment）等方式。我们表明，更重大的风险位于下一层，即代理与商务服务之间的协议。在那里，漏洞是结构性的：利用是确定性的，且独立于代理运行所用的模型，因此任何模型改进都无法消除它们。在三个主流平台上，我们识别出33个此类漏洞，每个漏洞无论部署何种模型都能确定性成功，且在实时测量的地方攻击成功率为100%。相同的失败模式在不同独立构建的代码库中反复出现，这是一种系统性模式而非孤立缺陷。其中三个漏洞串联起来可形成端到端的支付劫持。我们提出一个分类法，将这些结构性攻击与模型相关的语义攻击区分开来。我们还构建了两个工具：AIP-Bench（代理交互协议基准），据我们所知是第一个针对代理商务安全的确定性基准；以及PCAT（协议级商务代理信任），一种与平台无关的防御措施，可将五类结构性攻击中的四类（RC-1、RC-2、RC-4、RC-5）的结构性攻击成功率降至零，而RC-3（可观察的凭证通道）则降为仅警告，且无需修改任何平台。代理商务必须在协议层面而非仅模型层面进行安全防护。

## Abstract
Agentic commerce platforms let AI agents autonomously discover services, move payments, and wield user credentials on their users' behalf, and they already handle real money. Their security has so far been studied almost entirely at the level of the AI model, through prompt injection and misalignment. We show that the more consequential risks lie one layer down, in the protocol between agents and commerce services. There, vulnerabilities are structural : exploitation is deterministic and ndependent of which model an agent runs, so no model improvement removes them. Across three leading platforms we identify 33 such vulnerabilities, each succeeding deterministically regardless of the deployed model, at a 100% attack-success rate (ASR) wherever live-measured. The same failure modes recur across independently built codebases, a systemic pattern rather than isolated bugs. Three of them chain into an end-to-end payment hijack. We contribute a taxonomy separating these structural attacks from model-dependent semantic ones. We also build two artifacts: AIP-Bench (Agent Interaction Protocol Benchmark), to our knowledge the first deterministic benchmark for agentic commerce security, and PCAT (Protocol-level Commerce Agent Trust), a platform-agnostic defense that drives the structural attack-success rate to zero for four of the five structural classes (RC-1, RC-2, RC-4, RC-5), with RC-3 (observable credential channels) reduced to warn-only, without modifying any platform. Agentic commerce must be secured at the protocol layer, not only the model.

- **研究背景**：代理商务平台（Agentic Commerce Platforms）已允许 AI 代理自主完成服务发现、支付流转和凭证使用，处理真实资金，但现有安全研究几乎全部集中于模型层的语义攻击（如提示注入、模型错位），认为问题本质上是模型对齐问题。

## 2. 方法论

### 核心思想
- 形式化区分两种攻击类型：
  - **结构性攻击（Structural Attack，定义1）**：对平台 P 的任意语言模型配置 L，总存在某对手模型下的执行以概率 1 成功。漏洞位于协议层，模型改进无法修复。RC-1/2/3/5 完全确定性；RC-4（TOCTOU）在对手调度下确定性成立，随机调度下为正概率。
  - **语义攻击（Semantic Attack，定义2）**：成功概率依赖于语言模型配置，需模型层或语义验证防御。
- 建立六类根因分类法（RC-1~RC-6），自底向上从 33 个漏洞聚类得到。

### 关键技术细节
- 分析三类平台架构：CoralOS（Kotlin/Ktor 编排服务器、Solana 托管支付、MCP 客户端）、Fetch.ai uAgents（Python 去中心化框架、Almanac 注册表、DID 身份）、AP2（Google 代理支付协议、W3C 可验证凭证授权链）。
- 三种对手模型：恶意服务（ARS）、网络对手（ANET）、并发攻击者（ACONC）。
- 开发 **AIP-Bench**：首个确定性代理商务安全基准，采用确定性评判器（HTTP 状态码、钱包字符串匹配、日志模式正则、事件计数、模型字段等），避免 LLM 评判器的模型偏差。
- 开发 **PCAT**：平台无关 HTTP 中间件（sidecar），五项原则：
  - P1：注册表响应完整性验证（ECDSA P-256 签名 + 防重放）
  - P2：调用方 DID 身份绑定（真实 did:web 解析器）
  - P3：安全通道强制（URL 凭证检测警告、CSRF 阻断、重定向白名单校验）
  - P4：原子支付状态（asyncio.Lock + CAS 存储 + 回滚）
  - P5：MCP 工具调用授权（敏感工具要求 X-Caller-Identity 头）
- 形式化证明三个安全定理（P1 供应链保护、P3 CSRF 防护、P4 TOCTOU 消除）。

## 3. 实验设计

### 平台与场景
- **CoralOS**（v1.3.0，commit a38912b）：11 个漏洞，其中 10 个在 v1.4.0 仍存在，V7 已修复。V4（凭证在 URL）、V5（市场供应链 IPI）、V9（支付钱包劫持）等为实时验证。

### AIP-Bench 基准
- 覆盖所有漏洞场景，每项包含确切 API 调用序列、预期评判器输出、SHA-256 参考结果哈希、Docker Compose 一键复现环境。
- 全部 RC-1~RC-5 结构性场景 ASR 为 100%（RC-4 在对抗调度下）。

- 8 个模型 × 5 个提供商 × 3 个温度（0.0/0.3/0.7）× 3 种 IPI 变体 × 20 次试验 = **1440 次调用**。
- 模型：GPT-4o-mini、GPT-4o、Claude 3-Haiku、Claude Sonnet 4.6、Gemini 2.5 Flash、Gemini 2.5 Pro、Llama-3.3-70B、Mistral-large。

- PCAT 评估：对抗攻击套件通过中间件前后 ASR 对比 + 10,000 个良性请求的误报率 + 延迟微基准 + 并发吞吐（1/10/50/100 并发代理）。

### 对比方法

## 6. 主要结论与发现

- **系统性漏洞模式**：五个结构根因（RC-1~RC-5）在三个独立开发的平台上重复出现，属架构性失败模式。两大平台从中心化注册表获取代理定义而不做签名验证（RC-1）、全部三个平台在可观察通道放置凭证（RC-3）、两个平台实现非原子支付状态（RC-4）。
- **结构性漏洞成功率为 100%**：无论部署何种模型，所有结构性攻击均确定性成功。
- **攻击可链式化**：CoralOS 的 V5→V4→V9 构成完整支付劫持链（凭证窃取+行为操纵+支付重定向）。
- **模型抵抗呈梯度分布**：低端商业模型（GPT-4o-mini、Gemini Flash、Mistral）99-100% ASR；GPT-4o 68%；对齐训练模型（Claude 系列、Gemini Pro）0%；Llama-3.3-70B 10%。抵抗取决于对齐训练而非模型规模或层级（Claude 3-Haiku 为 Flash 层级却完全抵抗）。
- **PCAT 有效**：将四类结构攻击（RC-1、RC-2、RC-4、RC-5）在 HTTP 路径的 ASR 从 100% 降至 0%，RC-3 降为仅警告，10,000 良性请求零误报，延迟开销可忽略（P1 0.21 ms，P5 0.08 ms）。
- **防御必须分两层**：模型改进无法修复结构性漏洞，协议补丁无法阻止语义攻击，需双管齐下。

## 7. 优点

- **首次跨平台系统性研究**：覆盖三种不同架构风格的商业平台，具有广泛代表性。
- **正式的形式化区分**：明确定义结构性攻击与语义攻击，为未来研究提供理论框架。
- **确定性基准（AIP-Bench）**：避免 LLM 评判器的模型偏差和提示注入脆弱性，保证可复现、可跨模型比较。
- **实时验证成本透明**：记录实际 API 费用（$0.72 LLM 研究），提供 SHA-256 哈希和 Docker Compose 一键复现，实验可审计。
- **PCAT 平台无关设计**：无需修改平台源码，作为 HTTP sidecar 插桩；五项原则对应五类根因，设计可操作。
- **形式化安全证明**：三个定理给出密码学归约和协议逻辑论证。
- **负责任的披露流程**：协调披露、90 天禁运、公开时保留 PoC 代码位置，兼顾安全与透明。

## 8. 不足与局限

- **平台覆盖有限**：仅研究 3 个平台，未覆盖链上专属或全加密注册表等其他架构。
- **RC-4 结构性论证依赖调度假设**：在对抗调度下为 100%，在自然抖动下仅 30-57%（双进程），称“结构性”需依赖对“结构性”定义中的存在性量化。
- **LLM 行为研究覆盖有限**：部分模型表现温度依赖（Llama 10%→20%→0%），8 个模型 × 3 个变体仅能近似刻画边界；直接厂商复制的子集留待未来工作。
- **PCAT P4 分布式情况缺乏正式证明**：仅经验验证（Experiment D），无理论保证。
- **PCAT 部分原则依赖生态采用**：P1 只需注册表签名、P2 需要 DID 解析器和信任根；最小化部署下 P2 仅记录并放行，RC-2 仍暴露。
- **内部审计发现并修复了 4 个 PCAT 自身实现漏洞**，外部独立审查仍需进行。
- **PCAT 范围限制**：覆盖 HTTP 路径，不覆盖文件系统竞态、WebSocket 事件、内部 LLM 代理调用、密钥初始化等相邻层（14 个漏洞不在范围内）。
- **V4 修复不彻底**：仅警告而非阻断，彻底修复需平台将密钥移出 URL 路径。
- **实时资金流动未验证**：V9 因 faucet 速率限制未能在链上结算，仅止于协议层证明。
